# D-001: System boundary excludes payment processing and identity management

## Status
Proposed

## Decision
Campus Concierge's system boundary excludes real payment processing and university identity management. Authentication is delegated to the student's existing university login, and a deal's price is recorded as data only, using the category's fixed standard price, rather than transferred or held by the system.

## Evidence that changed our mind
An early design considered building in-app mobile money integration so the system could confirm payment automatically. This would require compliance, security and integration work far beyond what a semester project can deliver, and it is not necessary to solve the core problem: helping students get matched with a trustworthy, vetted helper and keep a record of what was agreed.

## Consequence we accept
The system cannot enforce that payment was actually transferred, so trust ultimately rests on the deal record and the dispute-report process rather than on an automatic payment confirmation. Using a fixed standard price per category, instead of per-errand negotiation, removes one source of disagreement but does not remove this one. Any identity-spoofing risk is inherited from whatever the university login already tolerates, since Campus Concierge does not build its own identity system.

## Next uncertainty to investigate
How reliably can the existing university login be treated as sufficient proof that a user is a real, currently enrolled student, and does the team need an additional lightweight trust signal, such as a verified student number, before a helper is vetted and registered?
