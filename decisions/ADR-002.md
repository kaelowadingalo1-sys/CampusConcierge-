# ADR-002: Interfaces, patterns and framework for the core workflow

**Status:** Accepted
**Builds on:** ADR-001 (modular application, Alternative A)

## Context

ADR-001 chose one modular application with one database, an identity check port and a notifier port. It named no patterns and no framework. Phase 2 needs implementable responsibilities, and three problems from earlier labs need a design answer: the identity and notification services are mocked or can be down (D-007, failure-recovery), posting must be atomic and race-safe (DI-1, DI-9, QS-5), and a notification outage must not fail a request (DI-11, DI-12).

## Decision

1. Use ports and adapters for identity, notifications and time (PD-1).
2. Use repositories inside a unit of work for all workflow persistence (PD-2).
3. Use a transactional outbox for notifications (PD-3).
4. Do not add a helper selection strategy interface (PD-R1) or a message broker (PD-R2).
5. Use TypeScript, Node.js and PostgreSQL, wired by hand with no dependency-injection container (`docs/framework-decision.md`).

## Alternatives considered

| Alternative | Why not |
|---|---|
| Core code calling the database and the Notification Service directly | Cannot test expiry without a real clock and a real outage; the transaction boundary would spread through the code |
| Broker plus separate services | See ADR-001 Alternative B and PD-R2 |
| Strategy interface for selection | Only one rule exists (PD-R1) |

## Consequences

- Good: the workflow rules can be tested with fakes, and the dependency direction is checkable (the core imports only `src/interfaces-or-ports/`).
- Cost: three ports and five repository-style interfaces to keep stable, and a dispatcher that must run.
- Risk: hand wiring grows with the number of adapters; if the composition file passes one screen, revisit the container decision.

## Verification

Post 50 errands at the same time against 20 helpers. Pass only if exactly 20 assignments are active, no helper has more than one, and 30 errands are in backlog.
